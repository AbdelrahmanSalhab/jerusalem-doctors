# Performance: after the October 2026 speed work

The same script and place as `2026-10-21-baseline.md`, after #100 (search in
one query) and #101 (dashboard cache, counts in SQL) were deployed. #104
(fonts) is not merged and not included.

## What changed, median time to first byte

| Path | Before | After | Change |
|---|---|---|---|
| Search `محمد` | 675 | 443 | −232 ms (−34%) |
| Search `الباطنية` (specialty) | 677 | 444 | −233 ms (−34%) |
| Search `هداسا` (hospital) | 692 | 435 | −257 ms (−37%) |
| Search `ا` (broad, 41 KB) | 700 | 431 | −269 ms (−38%) |
| `/dashboard` | 460 | 461 | no change at the median; 95th percentile 1553 → 578 |
| `/profile` | 468 | 416 | −52 ms |
| `/health` (reference: one tiny query) | 383 | 377 | same |

Search's server time is now about 139 ms (Server-Timing, median); the rest
of its ~440 ms is the network from Jerusalem to Frankfurt on a fresh
connection, which `/health` shows is ~380 ms on its own. A browser reuses
its connection, so a doctor typing a second search waits roughly the
server time plus one round trip.

The dashboard's median did not move: at 66 doctors, counting them was
cheap, and its time is the two sequential reads that remain (the signed-in
doctor, then their own workplaces and specialties). The cache removes the
slow outliers and keeps the dashboard from growing with the directory.
